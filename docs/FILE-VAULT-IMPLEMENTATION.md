# PhoneKey Files: current implementation

**Installation status, 28 Sep 2026:** PhoneKey Files was removed from the pilot laptop at the user's request. Its Send to shortcut, Ctrl+Shift+P hotkey, `.pkp` association, local binding, ProgramData trust copy, executable, and disposable test artifacts were removed. The source below is retained for possible future development; these usage instructions do not describe a currently installed feature. Existing user documents and any user-owned `.pkp` packages were not deleted. The Windows sign-in service was left running and unchanged.

PhoneKey Files is separate from the working Windows sign-in. None of its commands install, modify, or restart the Credential Provider or login service.

## Implemented

- The Windows file vault encrypts a new `.pkp` package with a random AES-256-GCM file key. The key is independently wrapped for the phone's separate Android Keystore P-256 agreement key and for a random 256-bit recovery code. New `PKP2` packages accept source files up to **1 TiB**, subject to available disk space. Old `PKP1` files remain readable.
- `PKP2` encrypts and authenticates 1 MiB chunks with distinct counter nonces under a fresh per-file key. Its header binds the exact file length, chunk size, and encrypted-envelope hash to both key wraps. Encryption rereads and decrypts the saved package to verify it. Phone-approved export and saved-code recovery write to a new temporary file and expose the requested output name only after every chunk, total length, and final hash verify. The phone QR uses the small package header, so its display does not wait for a full large-file scan.
- The phone signs a `PKB1` binding between its separate file key and the already paired PhoneKey identity. Windows verifies that signature before encrypting a file. The private phone file key never leaves Android Keystore.
- Every normal opening creates a fresh, 60-second, file-specific `PKF3` QR and a one-use return key. The laptop accepts plaintext only after it verifies the paired phone's signed proof and the returned file key. `PKP1` rereads the whole package; `PKP2` verifies its immutable prefix before opening and checks every encrypted chunk and the complete envelope hash while streaming. Expired, replayed, altered, and wrong-phone proofs are rejected.
- The Android app has a separate PhoneKey Files screen. Its file rendezvous retains an early Bluetooth file challenge until the matching QR is scanned, then requests biometric or device-credential approval. The corrected app built and passed Android unit tests and was installed in place on the paired TECNO after the first live scan exposed this race.
- The separate `phonekey-files` Windows tool implements `register`, `encrypt`, `view-text`, `open-to`, and `recover-to`. Encryption keeps the original plaintext file, creates a new package without overwriting an existing path, displays a recovery code, requires the user to re-enter that code, and verifies the saved package. `view-text` asks for fresh phone approval and presents up to 1 MiB of UTF-8 text in a read-only viewer without intentionally creating a plaintext output file. `open-to` is an explicit export for other file types: it also asks for fresh phone approval, then leaves a new unencrypted copy. `recover-to` requires the saved recovery code and creates a new unencrypted copy without phone approval.
- `Run-PhoneKeyFiles.ps1` displays a compact QR in a separate window with a live countdown and closes it after approval, expiry, or error. The disposable `phonekey-file-demo` uses the same QR writer and approval path.
- `Try-PhoneKeyFiles.ps1` remains available for picker-based encryption, text viewing, explicit phone-approved export, and recovery. The everyday pilot installs **Send to → Encrypt with PhoneKey** and a **Ctrl+Shift+P** shortcut for a selected file, and associates `.pkp` with `Invoke-PhoneKeyFile.ps1`. The shortcut opens a file picker if it cannot identify exactly one selected Explorer file. Double-clicking a `.pkp` requests fresh QR/fingerprint approval, opens a temporary plaintext copy in its default app, then asks the user to close the app before deleting that copy. No UAC is required for routine file operations. A direct static Explorer verb was registered but the live Windows 11 Explorer menu hid it even after a Shell association notification and restart; the installer removes those inert entries.

## Current verification and limits

The file tool now loads a separate **read-only copy of public pairing keys** from `%PROGRAMDATA%\PhoneKeyFiles\trust`. A one-time elevated setup copies those keys from the protected sign-in state without changing that state. Its directory and files grant SYSTEM and Administrators full access and standard Users read access only. The signed file-key binding stays in the current user's local profile. `check-setup` verified it under the signed-in Windows account, and a disposable file encrypted through the normal-user PowerShell launcher and recovered byte-for-byte with its code. The earlier path-not-found error occurred before recovery-code display; the new setup checks source and destination paths and reports the specific missing pairing path or binding.

The `PKP2` suite passed 40 library and six integration tests. A 64 MiB disposable file was encrypted and verified on this laptop, approved by the TECNO with a fresh file QR and fingerprint, exported, and matched the source SHA-256. The 1 TiB cap is a format/policy limit, **not** a tested 1 TiB round trip. Smart App Control was restored On after that test; the current optimized file tool launched and the new normal-user disposable encryption/recovery check passed with it On.

On 28 September, the new `.pkp` Windows association was installed and used to open the previously encrypted disposable text file. The first live launch found the phone but GATT service discovery failed before approval. A fresh launch reached the phone, verified its proof, and completed `OpenTo succeeded`. The user confirmed the text opened after fingerprint approval and that the cleanup prompt removed its temporary plaintext folder. The Explorer wrapper now offers one automatic fresh-QR retry for that exact transient service-discovery error. That retry behavior and common non-text apps still need live acceptance.

For daily pilot use, select a source file in Explorer and press **Ctrl+Shift+P**, or right-click and choose **Show more options → Send to → Encrypt with PhoneKey**. Save the printed recovery code separately and re-enter it. A new `<original-name>.pkp` is created beside the source; the original is **still unencrypted**. Double-click the `.pkp`, scan the QR in PhoneKey, approve with fingerprint, then close the opened document and acknowledge cleanup. Keep a recoverable backup of the `.pkp` and code. Do not remove your only original until you have successfully opened the package and stored its recovery code safely. The shortcut and Send to submenu have appeared in the user's Explorer; the current pairing-error retry still needs live confirmation.

Opening an arbitrary format in its normal app necessarily creates a temporary unencrypted file. The wrapper deletes its own copy after the document closes and the user clicks OK, but the app or Windows may retain caches, autosaves, or other traces. A crash before cleanup can leave the temporary file under `%LOCALAPPDATA%\PhoneKey\file-vault\opened`. `view-text` remains available for small UTF-8 files without intentional plaintext export. This pilot does not replace BitLocker and is not yet a signed, shareable product installer. Phone re-pairing requires an administrator to rerun the public pairing setup.
